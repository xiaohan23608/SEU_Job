# 东南大学计软智学院招聘信息系统 — 问题分析

## 1. 项目背景

东南大学学生在校期间需要关注各类企业招聘信息，包括校招、实习、内推等。当前信息获取渠道分散：

- 企业通过微信公众号推送招聘信息，但容易被淹没在大量消息中
- 学校就业信息网信息量大但展示形式单一，难以快速筛选
- 同学之间通过群聊转发，信息碎片化、易过期

**核心痛点：** 缺少一个面向东大学生的、轻量可控的招聘信息聚合展示平台，将分散的招聘信息（文本、图片、微信推送链接）以卡片形式统一展示，方便浏览和管理。

---

## 2. 问题定义

### 2.1 用户侧问题（东大学生）
| 问题 | 描述 |
|------|------|
| 信息分散 | 招聘信息散落在公众号、群聊、就业网等多个渠道，需要逐一查看 |
| 形式不统一 | 有的是纯文本、有的是图片、有的是微信推送链接，浏览体验不一致 |
| 访问控制 | 仅面向本校学生，不希望完全公开，需要简单密码验证 |

### 2.2 管理侧问题
| 问题 | 描述 |
|------|------|
| 内容来源多样 | 招聘信息可能是文本描述、截图、或微信推送链接，需要统一管理入口 |
| 更新频繁 | 岗位信息随时新增、修改、下架，需要便捷的编辑方式 |
| 权限保护 | 管理功能需要账号密码保护，防止未授权人员篡改 |

### 2.3 技术侧问题
| 问题 | 描述 |
|------|------|
| 数据可靠存储 | 需要使用数据库存储，保证数据持久化和查询效率 |
| 无需单独前端 | 管理员端直接在网页内完成编辑，不需要额外的管理后台应用 |
| 未来可扩展 | 预留 AI 自动整合文本生成卡片的能力，目前先手动编辑 |

---

## 3. 目标用户分析

### 3.1 访客端 — 东南大学在校学生
- **身份：** 东南大学在校本科生、研究生
- **需求：** 浏览招聘卡片 → 查看详情（文本/图片/链接）→ 决定是否关注
- **技术水平：** 普通用户，会用浏览器即可
- **访问方式：** 输入统一密码（`seucsjob`）登录后浏览

### 3.2 管理端 — 系统管理员
- **身份：** 项目维护者（你本人）
- **需求：** 新增招聘信息（文本/图片/链接）→ 编辑 → 下架过期信息
- **技术水平：** 能操作网页表单即可
- **访问方式：** 输入管理员账号密码后进入编辑模式

---

## 4. 可行性分析

### 4.1 技术方案选型

| 方案 | 优点 | 缺点 | 适用性 |
|------|------|------|--------|
| 纯静态 + JSON 文件 | 部署简单 | 不支持复杂查询，管理不便 | ❌ |
| Node.js + Express + JSON | 轻量、开发快 | 数据量大时查询效率低 | ❌ |
| **Node.js + Express + MySQL** | 关系型数据库，查询可靠，支持后续扩展 | 需要安装 MySQL | ✅ **推荐** |
| Python Flask + MySQL | 生态丰富 | 前后端分离成本稍高 | ✅ 可选 |

### 4.2 推荐技术栈

```
前端：HTML + CSS + JavaScript（原生，无需框架）
后端：Node.js + Express
数据库：MySQL
部署：本地/服务器直接运行
```

**选择理由：**
- MySQL 作为成熟的关系型数据库，数据可靠、查询高效
- 支持后续扩展（如 AI 生成内容的存储、多表关联等）
- Node.js + Express 开发效率高，适合此类中小型项目

---

## 5. 核心矛盾与解决思路

| 矛盾 | 解决思路 |
|------|---------|
| 安全性 vs 易用性 | 访客端使用统一密码验证，管理端使用独立账号密码，通过 Session 保持登录状态 |
| 内容形式多样 | 卡片支持文本、图片 URL、链接三种类型，统一存储和展示 |
| 无独立前端 vs 编辑体验 | 管理员端通过模态框/内联编辑实现，嵌入同一页面 |
| 当前手动 vs 未来 AI | 数据结构预留 `source` 和 `aiGenerated` 字段，方便后续 AI 模块接入 |
